# Vibe Check — Backend Security Audit for Flutter

This skill drives two deterministic, dependency-light bash scripts that live in this repo:

- `check_supabase_rls.sh` — probes named Supabase tables with the public anon key and reports whether RLS actually blocks unauthorized reads.
- `check_firebase_realtime_exposure.sh` — probes a Firebase Realtime Database path and reports whether it's publicly readable.

**Do not modify these scripts or their CLI interface.** They are the correctness-critical probing layer — plain HTTP requests with unambiguous pass/fail output. Your job is everything the scripts can't do on their own: find their inputs, decide what to probe, run them, and turn raw output into something a developer can act on.

## Step 1 — Discover credentials and project IDs safely

The Supabase **anon key** and the Firebase **project ID** are both meant to be public — they ship inside the compiled Flutter app, and RLS / Firebase rules (not secrecy of these values) are the actual security boundary. It's fine to work with these two specific identifiers. It is *not* fine to read a `.env` file wholesale: it may also hold genuinely sensitive values unrelated to this skill — a Supabase **service role** key, third-party API secrets, database passwords — that must never be pulled into context just to find these two.

Prefer this order, safest first:

1. **Let the script load `.env` itself.** `check_supabase_rls.sh` already auto-loads `SUPABASE_URL`/`SUPABASE_ANON_KEY` from a `.env` in the current or parent directory. If you can run from (or `cd` to) the Flutter project root, just invoke it with `--tables "..."` and no `--url`/`--key` — the anon key never has to pass through your context at all.
2. **If explicit values are required** (running from elsewhere, or the value isn't in `.env`), extract *only* the named identifier with a targeted match — e.g. `grep -E '^SUPABASE_URL=|^SUPABASE_ANON_KEY=' .env` — never open/print/paste the full file, and never surface unrelated `.env` lines.
3. Beyond `.env`, check:
   - `lib/main.dart` or any file calling `Supabase.initialize(url: ..., anonKey: ...)` — values may be inlined or reference constants; resolve them.
   - `lib/firebase_options.dart` (generated by FlutterFire CLI) for `projectId` in the relevant `FirebaseOptions` block.
   - `android/app/google-services.json` (`project_info.project_id`) or `ios/Runner/GoogleService-Info.plist` (`PROJECT_ID`) as a Firebase project ID fallback.
   - `.firebaserc` for the default Firebase project alias.

If nothing is found for a platform, ask the user directly for that value rather than guessing — never invent a URL, key, or project ID. Regardless of source, never print or echo the full contents of a `.env` file — only the specific identifiers this skill needs.

## Step 2 — Infer what to probe

Instead of making the user enumerate tables/paths, search the app's own code for what it actually reads/writes:

- Supabase: grep for `.from('...')` / `.from("...")` calls (the `supabase_flutter` / `postgrest` client pattern) to build the table list. Cross-reference with any SQL migration files (`supabase/migrations/`) if present.
- Firebase Realtime Database: grep for `FirebaseDatabase.instance.ref('...')` / `.reference().child('...')` calls to build the path list, plus check `database.rules.json` if it exists in the repo for declared top-level paths.

Present the inferred list to the user before probing so they can add/remove entries — don't silently probe things you're unsure about.

## Step 3 — Run the scripts

Invoke them exactly as documented in the README, using the discovered/inferred values as their existing flags. Prefer the `.env`-auto-load form for Supabase when possible (no `--url`/`--key` needed):

```bash
./check_supabase_rls.sh --tables "table1,table2,..."                                   # preferred: script loads .env itself
./check_supabase_rls.sh --url "$SUPABASE_URL" --key "$SUPABASE_ANON_KEY" --tables "..."  # only if .env auto-load isn't available
./check_firebase_realtime_exposure.sh "$FIREBASE_PROJECT_ID" "/inferred/path"
```

Run the Firebase check once per inferred path. Capture full output.

## Step 4 — Interpret results in context, not generically

For each table/path the scripts report as exposed:

- Explain *why it matters for this app*, based on what the code actually stores there (e.g. "the `messages` table is exposed and your `ChatScreen` writes `sender_id`/`recipient_id`/`body` into it — this is a full private-message leak, not a cosmetic issue").
- Prioritize findings (a leaking `users`/`profiles`/message table outranks a leaking `public_announcements` table).
- Generate remediation fitted to the real schema, not the script's generic example:
  - Supabase: write the actual `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` plus `CREATE POLICY` statements shaped to the table's real ownership column (e.g. `auth.uid() = user_id`), inferred from the migration files or query patterns found in Step 2.
  - Firebase: propose the specific `.read`/`.write` rule block for that path in `database.rules.json`, not a generic "add auth != null" placeholder.
- For tables/paths the scripts confirm are protected, note it briefly — don't over-report the negative case.

## Step 5 — Summarize and offer to apply fixes

Give the developer a short prose summary (not just raw script output): what's exposed, why it matters, what to fix first. Then offer to write the fix directly — e.g. add a migration file under `supabase/migrations/` with the RLS statements, or edit `database.rules.json` — and apply it if the user agrees.

## Notes

- This skill is for interactive use inside a Flutter project during development. The scripts themselves remain the right tool for CI / non-interactive use (see README) — this skill is a wrapper, not a replacement.
- If `.env` files aren't present and credentials can't be discovered anywhere, don't fabricate a probe — ask the user.
